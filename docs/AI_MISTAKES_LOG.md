# AI Mistakes Log

This log records real defects and mistaken assumptions encountered during development, how they were detected, and how they were resolved. Only genuine defects are recorded.

---

### Entry 1: Naive Environment Attestation in Session Handshake
- **Phase**: Phase 0 (Reconnaissance)
- **What was wrong**: In our first attempt to test the `/api/session` challenge handshake (`test_challenge.mjs`), we supplied placeholder dummy strings for the client environment attestation (`canvas: "1234567890abcdef"`, `gl: "abcdef1234567890"`).
- **How it was detected**: The mock store backend rejected `POST /api/session` with `HTTP 401 {"error":"unauthorized"}`.
- **Root cause**: The store backend calculates or validates expected canvas 2D rendering and WebGL driver hashes generated by client-side browser fingerprinting (`ar()` and `or()`).
- **How it was fixed**: We executed the exact `ar()` and `or()` algorithms inside a real headless Chrome instance via Chrome DevTools Protocol to extract the true hash signatures (`canvas: 'b93ad65b96d012a5'`, `gl: 'bb3723445bc1f3b4'`). Passing these authentic fingerprint hashes in the attestation payload enabled successful session token issuance (`HTTP 200`).

### Entry 2: Unchecked Upstream Error in Price Fetcher Causing JSON Parsing Crash
- **Phase**: Phase 0 (Reconnaissance)
- **What was wrong**: In `test_real_fp.mjs`, the script assumed `/api/products/:id/price` would always return HTTP 200 with an encrypted payload `{ e: string }`. When the upstream store intermittently returned `HTTP 503`, attempting to decrypt `pData.e` threw an unhandled `TypeError: The first argument must be of type string... Received undefined`.
- **How it was detected**: Caught by Node runtime stack trace during the execution of `test_real_fp.mjs`.
- **Root cause**: Upstream store deliberately returns 503 upstream errors intermittently.
- **How it was fixed**: Added explicit HTTP status code validation before attempting decryption, classifying 503 as `HTTP_5XX` and implementing exponential backoff retry.

### Entry 3: FakeDatabase Builder Did Not Support Chained `.select().single()` on `insert()`
- **Phase**: Phase 2 (Scraper Core & Integration Tests)
- **What was wrong**: In `fake-db.js`, `insert(rows)` returned an object `{ data, error }` directly instead of returning the query builder. When `scrapeProduct` and `acquireRunLock` chained `.insert(...).select('id').single()`, Node threw `TypeError: db.from(...).insert(...).select is not a function`.
- **How it was detected**: Caught by automated integration test execution (`npm run test:integration`).
- **Root cause**: Supabase Postgrest client v2 returns a chainable `PostgrestFilterBuilder` on `insert()` that allows selecting inserted fields before awaiting.
- **How it was fixed**: Updated `fake-db.js` so `insert()` saves the inserted rows in builder state and returns `this` builder, supporting subsequent `.select()`, `.single()`, and promise resolution (`then()`).

### Entry 4: Session Handshake HTTP 429 Mistakenly Classified as STRUCTURE_CHANGED
- **Phase**: Post-Phase 2 Real Store Smoke Test
- **What was wrong**: In `fetcher.js`, non-200 responses on `POST /api/session` were unconditionally assigned `errorType = STRUCTURE_CHANGED` without checking for HTTP 429 rate limiting.
- **How it was detected**: During real-store smoke test execution, session attempts returning `HTTP 429 {"error":"rate_limited","scope":"gate","retryAfter":1}` aborted immediately as `STRUCTURE_CHANGED` rather than backing off and retrying.
- **Root cause**: Over-eager structure failure logic overshadowed standard HTTP status code classification.
- **How it was fixed**: Updated `fetcher.js` to inspect `sessRes.status === 429`, parse the `retryAfter` field from the response body or headers, classify the error as `RATE_LIMITED`, and allow standard exponential/retry-after backoff before retrying.

### Entry 5: Documentation Diverged from Actual Codebase Constants
- **Phase**: Pre-Deployment Audit
- **What was wrong**: A documentation discrepancy emerged across `DESIGN_NOTE.md` and report summaries:
  1. The canvas and WebGL fingerprint hashes were mistakenly described as "copied from client-bundle.js", conflicting with Phase 0 recon which documented that they were generated by running the canvas fingerprinting routines in real Chrome via CDP on Windows (while the shared secret `'ine-mock-store-shared-k3y'` was extracted from `vendor-wasm.js`).
  2. Screen size was described in one place as `1920x1080`, whereas the code in `constants.js` defines `scr: [800, 600, 1]`.
  3. Cursor points were described as 8 coordinates, whereas `fetcher.js` generates 12 coordinates.
- **How it was detected**: Rigorous consistency audit between documentation files and code symbols.
- **Root cause**: Agent summary hallucination during multi-document generation without cross-referencing `constants.js` and `fetcher.js`.
- **How it was fixed**: Reconciled all documentation files (`PROTOCOL_EXPLAINED.md`, `DESIGN_NOTE.md`, `README.md`, and `walkthrough.md`) against the ground-truth code implementation.

### Entry 6: Uncached WebAssembly Compilation Adding CPU Load on Single-Core Cloud Environments
- **Phase**: Pre-Deployment Verification
- **What was wrong**: Every scrape invocation in `fetcher.js` re-compiled the base64 Wasm binary from scratch using `await WebAssembly.compile(buffer)`. While fast on a high-spec development laptop (~200–360 ms), this repeated compilation introduced CPU overhead that, combined with backoff retries, pushed scrape durations close to request timeouts on CPU-throttled free tier cloud instances.
- **How it was detected**: Benchmarking scrape phase breakdown and comparing cold vs. warm timings.
- **Root cause**: Treating WebAssembly module compilation as a per-request task rather than caching the immutable compiled `WebAssembly.Module` across scrapes.
- **How it was fixed**: Implemented in-memory `wasmModuleCache` in `fetcher.js` keyed by the Wasm payload. First compilation pays the initial compile cost, and all subsequent scrapes execute with zero compilation overhead (~0.0 ms). Raised request timeout to 15s and added configurable `SCRAPE_CONCURRENCY` (default 2) to prevent low-CPU throttling.
